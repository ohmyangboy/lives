# Lives 照片权限恢复：修正诊断 + 修复 + 交互设计

## 一、结论修正

用户实测推翻了"重置只是延迟生效"的旧结论。当前事实：

| 事实 | 证据 |
|------|------|
| App 内重置（仅 helper 2 条命令）执行成功但**无效** | 日志 5 次 `tccutil → exit 0`，弹窗从未重现；用户等待很久仍无弹窗 |
| 04:45:09 状态短暂读为 notDetermined、4 秒后变回 denied，用户未见弹窗 | 指向"重置清了 helper 记录，但下一次请求被**无弹窗自动拒绝**写回"，或"生效身份是主 App，helper 记录清了也没用" |
| 手动 4 条命令（**含主 App** `com.yangbukun.lives`）曾让弹窗重现 | App 内只重置 helper 2 条，可能漏掉了真正被拒绝的身份 |

**主嫌疑**：TCC 记录归属主 App（责任进程归属）或重置后被静默重新拒绝。由第一步的 TCC.db 快照定论。

## 二、代码修复（本次实施）

### A. 重置序列补齐为 4 条（核心修复，用户已验证有效）
`PhotoAuthorization.swift`：`resetDeniedAuthorization()` 改为依次执行：
- `tccutil reset PhotosAdd com.yangbukun.lives.photos-helper`
- `tccutil reset Photos com.yangbukun.lives.photos-helper`
- `tccutil reset PhotosAdd com.yangbukun.lives`（新增）
- `tccutil reset Photos com.yangbukun.lives`（新增）

### B. 去掉"提前返回"守卫
04:45:09 的 no-op（读到 notDetermined 直接返回、导致漏重置主 App）证明现有 `guard before == .denied else { return }` 会造成漏重置。移除该守卫——该函数只会在"denied 错误卡片"被触发，语境已保证当前处于拒绝态。重置后轮询校验逻辑保留（50 次 × 3s，作为诊断与传播延迟吸收）。

### C. photo-authorize 深度插桩 + "自动拒绝"识别
`PhotoLibraryWorker.requestAddOnlyAuthorizationDirect()`：
- 记录：进入时状态、requestAuthorization 调用时刻、回调触发时刻、返回状态 → 写入 `photo-reset.log`；
- 若回调在 <2s 内返回 `.denied`（不可能是人工点击）→ 识别为"系统未弹窗自动拒绝"，返回新错误码 `PHOTO_PERMISSION_PROMPT_SUPPRESSED`（recovery 引导复制命令/终端执行）。
这能在下一轮测试中一锤定音地区分"弹窗被拒"与"根本没弹窗"。

### D. 兜底：复制修复命令按钮（任何路径都不无声卡死）
- 新 native action `copyRepairCommands`：把 4 条命令写入 NSPasteboard（无需任何权限）；
- 前端在 denied / suppressed / pending 卡片上提供"复制修复命令"文字按钮。

### E. 交互设计落地（两个决策已确认：模态等待 + 渐进降级）

完整状态机（用户可见路径）：

| 状态 | 界面 | 动作 |
|------|------|------|
| 未询问 | 导出选择器含前置引导文案（已有） | 导出到照片 → 系统弹窗 |
| 系统弹窗 | 系统控制 | 允许 → 正常；不允许 → 恢复卡片 |
| **denied（第 1 次）** | 恢复卡片：主"重新授权并保存" / 次"改存到文件夹" / 文字"返回编辑" + "复制修复命令" | 主按钮 → 重置+轮询（模态等待） |
| **denied（第 2 次起）** | **渐进降级**：主"改存到文件夹"，"重新授权并保存"降为次按钮，文案调整为"已多次拒绝，可改用文件夹导出" | 尊重反复拒绝的选择（HIG：提供替代、尊重用户） |
| **恢复中** | 模态等待卡片"正在恢复照片授权（最多约 3 分钟，通常更快）"，取消按钮文案改为"取消恢复" | 状态翻转 → 自动继续导出 → 弹窗 |
| 轮询超时 | **专用 PENDING 卡**（告别红色"！"错误样式）：平静语调"系统同步中"，主"重新尝试" | 重新尝试 → 直接导出 |
| 自动拒绝（PROMPT_SUPPRESSED） | 恢复卡片 + 醒目提示"系统未弹出授权框"，主"复制修复命令" | 终端执行后重试 |
| restricted | 通用卡片（屏幕使用时间指引），不提供重置 | 改存到文件夹可用 |

实现要点：
1. `App.tsx`：deny 计数（localStorage `lives.photosDenyCount`，保存成功后清零）驱动渐进降级；`resetAndRetryExport` 加 token 防护——overlay 被取消/关闭后，残留的旧重置 promise 完成时**不得**触发第二次导出（日志显示曾出现 11 秒内两次并发重置，存在双重保存风险）。
2. `EntryPoint.swift`：重置动作串行化（single-flight，后到请求等待进行中的轮询结束后再执行），消除并发轮询。
3. `ExportOverlay.tsx`：新增 RESET_PENDING / PROMPT_SUPPRESSED 专属分支；运行态取消按钮按 stage 显示"取消恢复"；denied 卡加"复制修复命令"。
4. `nativeBridge.ts`：新增 `copyRepairCommands()`。

## 三、诊断协议（新包发布后一轮真机验证，产出定论）

用户在终端执行（终端需有"完全磁盘访问"；若无权限会报错，作为备选用 `log stream --predicate 'subsystem == "com.apple.TCC"'` 边复现边看）：
```
sqlite3 ~/Library/Application\ Support/com.apple.TCC/TCC.db "SELECT service, client, auth_value, datetime(last_modified,'unixepoch','localtime') FROM access WHERE client LIKE '%yangbukun%';"
```
- E0：基线快照（denied 态）→ **看 client 到底是 helper 还是主 App、service 是 Photos 还是 PhotosAdd**；
- E1：App 内"重新授权并保存"（4 条重置）→ 观察弹窗 → 快照对比；
- E2：若无弹窗 → 读插桩日志判断 PROMPT_SUPPRESSED + 快照对比（记录是否被复写）；
- E3：对照——终端手动 4 条 → 导出；
- E4：幂等验证（再拒绝 → 再恢复）。

## 四、结构性预案（若 E1/E2 显示 4 条重置仍无效）

把 PhotoKit 客户端从 LSUIElement helper 迁到主 App（`com.yangbukun.lives`，常规 Dock 应用）：Swift shim 编译为 cdylib 由 Rust FFI 调用（或 objc2-photos），在主 App 进程内完成 requestAuthorization + performChanges 保存。常规应用的 TCC 行为是有充分保障的主路径，可绕开 helper 的归属怪癖。本轮仅立项不实施。
